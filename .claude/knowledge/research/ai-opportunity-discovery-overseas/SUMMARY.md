# AI로 좋은 아이디어를 찾는 해외 방법론

## 결론

해외 연구와 실무를 종합하면 가장 강한 방식은 `AI 아이디어 생성기`가 아니라 **증거가 보존되는 상시 기회 발견 시스템**이다.

```text
원하는 제품 행동 결과
  → 실제 고객 신호 수집
  → 원문 보존·중복 제거·세그먼트 연결
  → 사람이 만든 초기 코드북
  → AI의 대량 코딩과 독립 검수
  → 고객 여정별 기회 지도
  → 과거 행동을 묻는 고객 인터뷰
  → 복수 솔루션의 위험 가정 비교
  → 실제 행동 실험
  → 출시 후 결과를 원래 가설에 다시 연결
```

핵심 원칙은 세 가지다.

1. 커뮤니티·후기는 **후보 문제를 찾는 레이더**이고 최종 판사가 아니다.
2. AI는 자유로운 의미 해석보다 명확한 코드북을 적용하는 구조화 작업에 더 안정적이다.
3. 좋은 아이디어의 근거는 AI 페르소나의 호평이 아니라 실제 사람의 과거 행동과 실제 전환이다.

## 해외 근거가 추가한 중요한 정정

### 1. 대량 VOC만으로 기회를 확정하면 안 된다

[Teresa Torres의 Opportunity Solution Tree 공식 가이드](https://www.producttalk.org/opportunity-solution-trees/)는 기회를 고객의 필요·불만·욕구로 정의하고, 구체적인 과거 행동 이야기를 묻는 인터뷰에서 찾으라고 권한다. 판매 대화, 지원 티켓, 기능 요청과 행동 분석은 유용하지만 맥락이 부족하므로 후속 인터뷰 주제를 정하는 입력으로 쓰는 편이 안전하다고 설명한다.

따라서 모요식 커뮤니티 마이닝의 고도화 버전은 다음과 같다.

```text
커뮤니티 반복 불만 발견
  → 해당 불만을 실제로 겪은 사람 모집
  → “마지막으로 그 일을 했던 때”의 구체적 행동 복원
  → 문제 순간·대안·비용·결정 요인 확인
  → 기회로 승격 또는 폐기
```

### 2. AI는 귀납적 발견보다 연역적 대량 코딩에 강하다

2026년 PLOS Digital Health의 [인간 분석자와 LLM의 블라인드 비교 연구](https://doi.org/10.1371/journal.pdig.0001189)는 사전 정의된 코드북을 적용하는 연역적 코딩에서 LLM 평균 일치율 93.5%, 인간 분석자 92.7%를 보고했다. 그러나 열린 주제를 발견하는 귀납 분석에서는 모델별 편차가 컸고, 엄격한 환각률은 1.2%였지만 부분 일치와 화자 오류까지 포함한 종합 오류율은 12.4%였다.

연구가 사용한 안전장치는 제품 리서치에도 그대로 적용할 수 있다.

- 전역 코딩 규칙을 먼저 고정
- 모든 코드에 원문 인용과 segment ID 요구
- 인간과 AI 분석을 서로 블라인드 처리
- 독립 합의 패널로 차이를 판정
- 단순 환각뿐 아니라 부분 일치·화자 혼동까지 오류로 측정

### 3. 평균 정확도보다 세그먼트별 편향을 봐야 한다

World Bank의 [Using Large Language Models for Qualitative Analysis Can Introduce Serious Bias](https://documents.worldbank.org/en/publication/documents-reports/documentdetail/099433311072326082)는 LLM의 인터뷰 주석 오류가 무작위가 아니라 인터뷰 대상자의 난민 여부·인구통계·교육·소득 같은 특성과 연관될 수 있음을 보였다. 이런 오류로 후속 통계 결론까지 달라질 수 있었다. 저자들은 최소한 일부 자료를 전문가가 직접 코딩해 편향을 측정하고, 맥락이 중요한 경우 그 인간 코딩을 기반으로 별도 모델을 훈련하는 방식을 권한다.

따라서 전체 정확도 하나로 통과시키지 말고 다음을 분리 측정해야 한다.

- 고객 세그먼트별 거짓 양성·거짓 음성
- 희귀 문제와 다수 문제의 오류율
- 구매 단계별 코드 일치율
- 직접 발화와 연구자·상담원 발화의 혼동
- 국가·언어·문화권별 오류율

### 4. 합성 사용자는 발견 보조이지 수요 검증 수단이 아니다

182개 연구를 종합한 [Synthetic Participants Generated by Large Language Models: A Systematic Literature Review](https://www.researchsquare.com/article/rs-9057643/v1)는 네 가지 공통 문제를 정리했다.

- 인간과 다른 인지 구조
- 응답 분포의 왜곡
- 그럴듯해서 더 위험한 가짜 현실감
- 학습 데이터의 암기·오염 가능성

논문은 합성 사용자를 실제 참가자의 대체재보다 휴리스틱 도구로 보라고 제안한다. 아이디어 반론, 인터뷰 질문 초안, 누락 관점 탐색에는 쓸 수 있지만 문제의 존재·선호·지불 의사를 증명하는 데이터로 세면 안 된다.

## 권장 운영체계

### 단계 0. 원하는 결과를 먼저 정한다

기회 지도의 맨 위에는 기능이 아니라 고객 행동으로 표현한 제품 결과를 둔다.

```text
나쁜 예: AI 아이디어 추천 기능 출시
좋은 예: 첫 방문자가 7일 안에 검증 행동 하나를 시작하는 비율 증가
```

Opportunity Solution Tree는 사업 결과, 제품 결과, 기능 사용량을 구분하며 발견 활동에는 팀이 직접 영향을 줄 수 있는 제품 행동 결과를 권한다.

### 단계 1. 신호 호수를 만든다

한 채널의 빈도에 끌려가지 않도록 다음 자료를 함께 넣는다.

- 고객 인터뷰와 관찰
- 커뮤니티·리뷰·검색어
- 상담·지원 티켓
- 영업 통화·실패 거래·CRM
- 제품 사용 행동과 이탈 구간
- 결제·해지·환불·재구매 데이터
- 경쟁 제품의 변화와 대안 행동

해외 상용 제품도 이 방향이다. [Productboard Spark](https://www.productboard.com/product/spark/)는 고객 피드백·시장 신호·전략·제품 맥락을 연결하고, [Bagel Discovery OS](https://bagel.ai/platform-overview/bagel-discovery-os/)는 Gong·Salesforce·Zendesk·Jira·Slack 등의 신호를 매출 맥락과 묶는다고 설명한다. 이는 벤더의 제품 설명이며 성과가 독립 검증됐다는 뜻은 아니다.

### 단계 2. 증거 장부를 고정한다

모든 자료를 한 문장 단위의 `evidence atom`으로 만든다.

```json
{
  "evidence_id": "E-001",
  "source_id": "interview-07",
  "source_type": "customer_interview",
  "raw_quote": "...",
  "speaker_role": "buyer",
  "journey_moment": "compare",
  "past_behavior": "판매자 5명에게 개별 문의",
  "workaround_cost": "2시간",
  "segment": "high-price-sensitivity/high-search-willingness",
  "consent_class": "internal-research",
  "source_hash": "..."
}
```

원문은 읽기 전용으로 두고, 관찰·해석·추천을 별도 필드로 분리한다.

```text
원문 → 관찰 → 코드 → 테마 → 기회 → 추천 → 실험
```

최근 공개된 OSS 프로토타입 [discovery-agents-handoff](https://github.com/klausners/discovery-agents-handoff)는 인용문을 SHA-256으로 잠그고, 변조되면 쓰기를 중단한다. 아직 별점 0개의 초기 프로젝트이므로 채택 증거는 아니지만, 증거 무결성을 구현하는 구체적인 참고 사례다.

### 단계 3. 인간이 초기 코드북을 만든다

AI에게 처음부터 테마를 전부 만들게 하지 않는다.

1. 고객 여정과 세그먼트를 나누어 대표 자료를 표본 추출한다.
2. 연구자 두 명이 독립적으로 1차 코딩한다.
3. 불일치를 토론해 코드 정의·포함·제외 예시를 만든다.
4. 희귀하지만 중요한 문제와 반대 증거를 별도 코드로 둔다.
5. 코드북을 고정한 뒤 AI가 전체 자료에 적용하게 한다.

AI의 자유 탐색은 고정 코드북 밖의 새로운 신호를 제안하는 `unknown` 통로로만 유지한다. 제안된 새 코드는 사람이 승인하기 전까지 기회 점수에 반영하지 않는다.

### 단계 4. 생성자와 판정자를 분리한다

[Anthropic의 Building Effective Agents](https://www.anthropic.com/research/building-effective-agents)는 복잡성을 필요한 만큼만 추가하고, 명확한 기준이 있을 때 생성자와 평가자를 분리하는 evaluator-optimizer 구조를 권한다. 아이디어 발견에는 다음 역할 분리가 적합하다.

| 역할 | 책임 |
|---|---|
| Extractor | 원문에서 행동·문제·대안·비용 추출 |
| Coding Agent | 고정 코드북 적용 |
| Fidelity Critic | 코드가 인용문으로 실제 지지되는지 검사 |
| Segment Auditor | 특정 집단의 과대·과소 분류 검사 |
| Opportunity Synthesizer | 중복 없는 기회 구조 작성 |
| Dissent Agent | 반대 증거·이미 만족한 사용자·대안 탐색 |
| Human Adjudicator | 새 코드 승인과 최종 전략 판단 |

단순 수집·해시·중복 제거·개수 계산·출처 검사는 코드로 결정적으로 처리하고, 문맥 판단이 필요한 부분만 LLM에 맡긴다.

### 단계 5. 기회를 고객 여정으로 구조화한다

Opportunity Solution Tree의 공식 방법을 적용하면 다음 순서다.

1. 인터뷰의 전체 경험 지도를 만든다.
2. 경험의 주요 순간을 상위 기회로 둔다.
3. 개별 문제를 발생 순간 아래 배치한다.
4. 부모·자식·형제 관계를 한 가지씩 정리한다.
5. 세 번에서 네 번의 고객 이야기를 추가할 때마다 지도를 갱신한다.

기회와 솔루션을 구별하는 검사는 간단하다. **이 문장을 해결할 방법이 두 개 이상 있는가?** 하나뿐이라면 대개 솔루션을 문제처럼 적은 것이다.

### 단계 6. 기회는 네 영역으로 평가한다

Teresa Torres가 제시한 네 영역을 사용한다.

1. Opportunity sizing: 몇 명에게 얼마나 자주 발생하는가?
2. Market factors: 해결하면 시장 위치가 어떻게 달라지는가?
3. Company factors: 미션·비전·전략과 얼마나 맞는가?
4. Customer factors: 고객에게 얼마나 중요하며 현재 대안 만족도는 어떤가?

이 단계에서는 구현 공수를 넣지 않는다. 공수는 특정 솔루션의 속성이며 같은 기회에도 쉬운 해결책과 어려운 해결책이 공존할 수 있기 때문이다.

### 단계 7. 상위 기회를 실제 사람에게 재검증한다

상위 후보마다 최소한 구체적인 과거 행동 이야기를 수집한다.

```text
마지막으로 이 문제를 겪었던 때를 처음부터 설명해주세요.
그때 무엇을 하려고 했나요?
어떤 대안을 먼저 시도했나요?
시간이나 돈을 얼마나 썼나요?
결정을 바꾼 순간은 무엇이었나요?
결국 하지 않았다면 왜 멈췄나요?
```

커뮤니티 빈도가 높더라도 구체적인 행동·대안·비용이 나오지 않으면 우선순위를 낮춘다.

### 단계 8. 한 기회에 복수 솔루션을 비교한다

하나의 타깃 기회에 최소 세 가지 해결 방향을 만들고, 각 솔루션의 가치·사용성·실행 가능성·사업성 가정을 분해한다. 그중 가장 위험한 가정을 가장 작은 실험으로 비교한다.

AI는 다음에 사용한다.

- 서로 다른 해결 원리 생성
- 숨은 가정 목록화
- 실패 조건과 반증 데이터 제안
- 인터뷰·프로토타입 실험안 초안

AI 페르소나의 선호 투표는 검증값으로 사용하지 않는다.

### 단계 9. 증거 사다리를 실제 행동까지 올린다

```text
언급 → 과거 해결 행동 → 클릭 → 시작 → 유효 신청
→ 거래·결제 → 반복·유지 → 추천 → 단위경제성
```

모요의 약 100건 신청은 `유효 신청` 부근의 강한 신호다. 다음 판정에는 계약 완료율, 취소율, 획득비용, 건당 마진과 재구매·추천이 필요하다.

### 단계 10. 출시 후 원래 기회로 되돌아간다

상용 제품들의 2026년 방향은 발견을 일회성 문서가 아니라 상시 시스템으로 만드는 것이다. 새 고객 신호, 제품 행동과 출시 결과를 원래 기회·가설·실험에 다시 연결해야 한다. 그래야 처음의 문제 정의가 맞았는지와 해결책만 틀렸는지를 구분할 수 있다.

## 모요 방식의 최종 역설계

모요가 공개한 과정은 해외의 고급 패턴과 상당히 맞는다.

| 모요에서 보인 것 | 해외 근거와 결합한 해석 |
|---|---|
| 커뮤니티·후기 대량 수집 | 기회 후보를 넓게 찾는 신호 레이더 |
| 자동 라벨링·분류 | 코드북 기반 대량 코딩으로 구현할 때 신뢰도 상승 |
| 가격 민감도 × 탐색 의지 | 세그먼트별 문제와 행동 차이를 보기 위한 축 |
| context 파일 | 분류 정의·제품 원칙·완료 기준의 고정 메모리 |
| 역할별 agents | 생성·검수·판정을 분리하는 evaluator 구조 |
| 실제 신청 약 100건 | 합성 반응이 아닌 행동 증거 |

공개 글에 보이지 않는 가장 중요한 보완점은 세 가지다.

1. 자동 분류 전 사람이 만든 기준 코드북과 세그먼트별 오류 측정
2. 커뮤니티 발견 뒤 구체적인 과거 행동 인터뷰로 맥락 보완
3. 신청 이후 거래·마진·유지까지 연결되는 증거 사다리
