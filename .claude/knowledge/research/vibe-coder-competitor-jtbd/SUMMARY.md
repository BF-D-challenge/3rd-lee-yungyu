# 종합 판정

## 한 줄 결론

`Vibe-to-Real Doctor`를 **보안·품질 스캐너로 만들면 이미 늦었다.** 직접 경쟁사들은 URL 한 개, 무료 점수, AI fix, 재검사, badge, monitoring까지 거의 같은 흐름을 제공한다. `Agent Control Room`도 Conductor·GitHub·Cursor가 작업 격리부터 PR 회수까지 빠르게 흡수하고 있다.

## 경쟁이 증명한 진짜 JTBD

두 시장의 공통 뿌리는 다음과 같다.

> AI에게 실행은 맡기되, 내가 이해하지 못한 결과 때문에 사용자·돈·평판을 잃지 않도록 통제와 증거를 유지하고 싶다.

경쟁사들은 이 Job을 다음 세 구간에서 해결한다.

1. **코드 증거:** PR·소스에 버그와 취약점이 없는가?
2. **작동 증거:** 로그인·결제 등 핵심 흐름이 계속 작동하는가?
3. **실행 증거:** 에이전트가 무엇을 바꿨고 어떤 검증을 통과했는가?

## 비어 있지 않은 아이디어

- URL을 넣으면 보안 점수를 주는 제품
- AI용 수정 프롬프트를 주는 제품
- 수정 후 재검사와 인증 badge를 주는 제품
- 여러 coding agent 상태를 보여주는 dashboard
- repo를 worktree로 나눠 병렬 실행하는 Mac app

모두 이미 실제 제품이 있고, 일부는 무료·무가입 진입까지 제공한다.

## 상대적으로 비어 있는 JTBD

경쟁 제품이 거의 해결하지 않는 질문은 코드가 아니라 **제품을 계속할 이유**다.

> AI로 만든 앱이 기술적으로 작동하지만 더 시간을 쓰거나 광고비를 태울 가치가 있는지 모를 때, 실제 목표 고객의 행동으로 가장 위험한 가정을 시험해줘서, 기능을 더 만들기 전에 계속·수정·중단을 결정하고 싶다.

기존 제품의 답은 `취약점 3개`, `PR passed`, `로그인 flow 정상`이다. 하지만 다음 질문에는 답하지 않는다.

- 이 문제가 실제로 중요한가?
- 사용자가 현재 어떤 대안을 쓰는가?
- 랜딩을 본 사람이 시간·연락처·돈을 걸 것인가?
- 누구에게 어떤 메시지가 먹히는가?
- 이번 주 더 만들지, 메시지를 바꿀지, 중단할지?

## 현재 Idea Lab이 차지할 수 있는 자리

Idea Lab을 `아이디어 생성기`에서 `Idea Trial`로 재정의한다.

```text
아이디어 또는 현재 앱 URL
→ 한 문장 JTBD와 가장 위험한 가정 추출
→ 두 메시지·랜딩 실험 생성
→ 소액 광고 또는 목표 고객 모집
→ 실제 행동 비교
→ 계속 / 수정 / 중단 판정
→ 승자만 coding agent 작업 티켓으로 전환
```

경쟁 스캐너가 `코드가 안전한가?`를 답한다면 Idea Trial은 `애초에 이것을 더 만들어야 하는가?`를 답한다.

## 더 좁은 대안: JTBD Acceptance Test

광고 운영까지 하기 어렵다면 먼저 아래로 축소한다.

1. 사용자가 앱 URL과 “누가 어떤 순간에 무엇을 끝내야 하는지”를 입력한다.
2. 제품이 그 JTBD를 수행하는 실제 브라우저 시나리오를 만든다.
3. 정상 경로뿐 아니라 빈 데이터·권한 차이·결제 실패·모바일을 실행한다.
4. 결과를 기술 경고가 아니라 `사용자는 목표를 완료할 수 있음/없음`으로 보여준다.
5. 코딩 에이전트가 수정한 뒤 같은 JTBD로 재검증한다.

이 방향은 Checkly의 synthetic monitoring과 일부 겹친다. 차별점은 Playwright를 아는 개발자가 아니라, **자기 제품의 JTBD만 설명할 수 있는 비개발 빌더**를 입력 사용자로 삼는 것이다.

## 권장 우선순위

| 후보 | 경쟁 강도 | 사용자 긴급성 | 결제 가능성 | 방어 가능성 | 판정 |
|---|---:|---:|---:|---:|---|
| 범용 vibe security scanner | 매우 높음 | 높음 | 중간 | 낮음 | 중단 |
| 범용 agent control room | 매우 높음 | 높음 | 높음 | 매우 낮음 | 중단 |
| JTBD Acceptance Test | 중간 | 높음 | 중간~높음 | 중간 | 제한적 실험 |
| 실제 수요를 판정하는 Idea Trial | 낮음~중간 | 중간 | 미검증 | 중간~높음 | 가장 먼저 학습 |

## 가장 위험한 가설

> 바이브 코더는 더 좋은 아이디어나 더 많은 진단 결과가 아니라, 실제 고객 행동을 얻기 위해 앱 URL·광고비·연락처 또는 시간을 맡길 의향이 있다.

## 다음 실험

- 대상: 배포했지만 실제 사용자가 10명 미만인 바이브 코더 10명
- 수동 제공: 앱과 랜딩을 보고 가장 위험한 가정 하나, 메시지 2개, 모집 채널 1개를 만들어 7일간 대신 운영
- 비용 있는 행동: 광고비 5만원 또는 목표 고객 5명에게 직접 연락 권한 제공
- 성공: 10명 중 4명이 비용을 맡기고, 3명이 결과에 따라 기능·메시지·중단 결정을 실제 변경
- 반복 신호: 2명이 다음 아이디어나 기능에서도 다시 실험 요청
- 중단: 진단은 원하지만 광고비·고객 접촉을 맡기지 않으면 제품 운영이 아니라 조언 콘텐츠만 원한다는 뜻

## 조사 한계

- 경쟁사 공식 페이지는 제공 기능과 가격을 확인하는 근거다. 실제 고객 수, 매출, 탐지 정확도, 리텐션은 검증하지 않았다.
- 비슷한 신규 보안 제품이 많다는 사실은 수요와 동시에 낮은 진입 장벽·SEO 복제 경쟁을 의미할 수 있다.
- 실제 제품 방향은 경쟁사 수가 아니라 목표 사용자의 비용 있는 행동으로 판정해야 한다.
